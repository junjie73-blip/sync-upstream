# 下一版计划

本页写的是**已经确认存在、但 0.3.0 没有做的功能点**，按影响排序，作为下一个小版本（0.4.x）的候选清单。它是计划而不是承诺：具体做哪几项、什么顺序，取决于实际使用中的反馈。

每条都写清三件事：现在会怎样、下一版打算做什么、在这之前怎么绕过。如果某一条对你特别重要，欢迎带着用例反馈——这决定优先级。

## 1. 英文覆盖到运行日志与子命令正文

现在 `--lang en` 只把**帮助文本**、**参数报错**、**错误消息**和 **`init` 问答**换成英文；一次同步的过程日志、同步流程里的补全问答与冲突询问、配置摘要、`status` / `doctor` / `why` / `history` 的输出正文、git 诊断信息、灰度与通知的文案仍然是中文。日志文件里因此会是中英混排。

下一版打算把这些文案也纳入同一套语言键，并让以库方式调用的程序能在代码里切换语言。

在这之前：需要机器可读内容时用 `--json`。它的字段名和判定标识都是英文（`already-synced`、`delete-protected`、`ignored`……），不受语言影响；只有 `note`、`doctor` 的 `message` 这类说明性文字还是中文。

## 2. 撤销指定一次同步，而不只是最近一次

现在 `-uo` / `--undo` 只还原状态文件里记录的最后一次同步，且要求那次同步提交仍然正好是分支的当前顶端；更早的记录能在 `history` 里看到，但没有对应的撤销入口。撤销本身是追加一次新提交，不改写已经推送的历史，所以远端还要再把这次撤销推上去。

下一版打算让 `--undo` 接受 `history` 给出的序号或时间，并明确列出这次撤销会改动哪些路径。

在这之前：`history --json` 能拿到每次同步的提交号，对它执行 `git revert <提交>` 就是手工版的撤销（HEAD 已经领先时，`--undo` 拒绝改动并给出同样的建议）。

## 3. 状态文件自动进 `.gitignore`

`.sync-state.json` 是本地增量状态，单上游时它在内置忽略清单里；多上游时每个上游各写一份 `.sync-state-<名>-<哈希>.json`，这些名字带哈希，不在清单内，于是每次同步后都会出现在未跟踪文件列表里。`doctor` 会用一条 `state-ignore` 提醒。

下一版打算在 `init` 与 `--generate-config` 时把需要的忽略条目一并写好（可以关掉）。

在这之前：手工加一行 `.sync-state*.json` 到 `.gitignore`。

## 4. 多上游也能灰度

灰度发布、`--full-release`、`--rollback` 目前只在单上游时可用；配置里有多个上游时这几个参数会被直接拒绝（退出码 2）。多个上游指向重叠目录时，排在后面的那个覆盖前面的，运行不会为此单独告警。

下一版打算把灰度的选择范围按上游划分，并在目录重叠时给出明确清单。

在这之前：一次只汇入一个上游，或先让重叠目录归属唯一上游。

## 5. 凭据不落明文

`pat` 与 `user_pass` 两种认证方式会把凭据写进 `.git/config` 里 remote 的 URL，同机其它进程可读。`ssh` 不受影响。

下一版打算优先使用 git 的凭据助手，并支持凭据来自环境变量引用而不是配置文件明文。

在这之前：用 `ssh`，或把带凭据的仓库单独放一个只在同步时才可读的工作区，并同步完就清理 `.git/config` 里的 URL。

## 6. 没有 CLI 时也能建 PR

PR 模式（`--pr`）本身不依赖外部工具：改动会推到自动分支并给出对比链接。但要"顺手把 PR 建出来"，现在必须本机装有对应的命令行工具，否则只会打印链接。

下一版打算在没装工具时改用平台 API 建 PR（凭据复用现有认证配置）。

在这之前：按打印出来的对比链接手工创建，或安装对应平台的命令行工具。

## 7. 一次问多个路径的判定结果

`why` 现在一次只接受一个路径，返回这个文件这次会不会被同步以及原因（命中了哪条忽略规则、是否已是最新、是否被删除策略保留、是否落在灰度范围外……）。批量排查只能一个文件一个文件跑。

下一版打算让它接受目录和多个路径，并按原因分组汇总。

在这之前：`status --json` 里每个来源都带 `plan.skipped` 列表（每项有 `path` 与英文的 `reason`），配合 `jq` 按 `reason` 分组比逐个跑 `why` 快得多。

## 8. 更多通知渠道

现有渠道是 `stdout`、`http`、`slack`、`dingtalk`、`wecom`。飞书（Lark）没有内置渠道，只能用 `http` 自己拼载荷；`http` 也不支持自定义签名头。

下一版打算补上飞书渠道，并给 `http` 渠道加自定义请求头与签名。

在这之前：用 `http` 渠道对接平台自带的 Slack 兼容入口，或在接收端做转换。

## 9. 定时轮询，不必暴露端口

自动同步目前靠 Webhook 守护模式（需要能被访问的端口）或外部定时任务。GitHub Actions 的定时任务是最常见的替代，但要自己写工作流。

下一版打算提供内置的轮询模式（按间隔拉取上游、没有变化就安静退出）与一份可直接复制的流水线模板。

在这之前：用系统的计划任务或 CI 定时任务跑 `sync-upstream`，配合 `--lock-wait` 避免与手工运行相撞。
